# Specification — 점심 추천 (WHAT / WHY)

> 기술(HOW)은 여기 쓰지 않는다. 설계는 [plan.md](plan.md) 참조.

## 1. 문제 정의 (Why)
매일 반복되는 "점심 뭐 먹지" 결정 피로. 회사 주변 선택지는 많지만 늘 가던 곳만 가거나 고르기 귀찮다. **한 번의 클릭으로 회사 주변에서 랜덤하게, 단 최근에 추천된 곳은 빼고** 한 곳을 정해주면 결정 비용이 사라진다. 나아가 추천 식당의 업종/대표 카테고리에서 **대표 메뉴 힌트**까지 함께 제시해 "식당"뿐 아니라 "뭘 먹을지(메뉴)"도 거든다.

## 2. 사용자 (Who)
회사(특정 사옥) 근처에서 일하는 개인. 로그인 없이 즉시 사용. 주 사용 시간대는 평일 11:30~13:00, 모바일.

## 3. 핵심 유즈케이스 (What)
- **UC1 추천받기**: 사용자가 "오늘 점심 추천" 버튼을 누르면, 회사 중심 반경 내 음식점 중 **최근 추천 이력에 없는** 한 곳을 무작위로 골라 보여준다.
- **UC2 다시 추천**: 결과가 마음에 안 들면 "다른 곳" 버튼으로 즉시 다른 한 곳을 다시 뽑는다(방금 것도 제외).
- **UC3 메뉴 힌트·상세**: 추천 식당의 업종/카테고리에서 도출한 **대표 메뉴 힌트**(예: 국밥, 돈카츠, 파스타)를 보고, "카카오맵에서 보기"로 실제 메뉴·위치·리뷰를 확인한다.
- **UC4 이력 확인/초기화**: 최근 추천된 목록을 보고, 원하면 이력을 초기화한다(다시 전체가 후보가 됨).
- **UC5 추천 로직 설명**: 타이틀 옆 '?' 아이콘을 누르면, 반경·야간업종 제외·최근 이력 제외·랜덤 선택·메뉴 힌트 근거를 요약한 설명이 레이어 팝업으로 뜬다. 설정값(반경·최근제외 개수 등)이 바뀌어도 설명이 그 값을 그대로 반영해 실제 동작과 어긋나지 않는다.
- **UC6 모락모락 오늘의 메뉴 보기**: 사용자가 "모락모락" 탭을 열면, **GitHub Actions 예약 크롤러가 서버사이드로 수집해 레포에 커밋한** 회사 구내식당(풀무원 모락모락)의 오늘의 메뉴를 코너별로 확인한다. 데이터를 가져오지 못하거나(네트워크·빈 응답·파싱 오류 어떤 사유든) 가져온 데이터가 **오늘(KST) 날짜로 갱신되지 않았으면(날짜 불일치)**, 오류 메시지 대신 "준비중입니다" 안내로 통일해 보여준다.
- **UC7 점심메뉴 월드컵**: 사용자가 "월드컵" 탭을 열면, 탭1이 수집한 반경 내 실제 후보 식당 중 메뉴 힌트가 있는 곳들로 16강 토너먼트(16강~결승 15경기)를 진행해 하나를 뽑는다. 최종 우승 시 실제 식당명과 카카오맵 링크를 확인한다.

## 4. 기능 요구 (What, not How)
- **회사 위치**: `서울특별시 성동구 아차산로13길 11` 을 중심으로 한다.
- **거리 제한**: 회사로부터 **도보 15분 이내** 식당만 후보로 한다. (도보 15분 ≈ 직선 약 1,000m 로 근사 — 근거·조정은 [plan.md](plan.md))
- **점심 영업 제약**: **점심 시간대에 영업하는 식당만** 후보로 한다.
  - ⚠️ 한계: Kakao 검색 API는 **영업시간을 제공하지 않아** "점심 영업 중"을 데이터로 보장할 수 없다. 따라서 아래로 **근사**한다(§8 참조):
    - (자동) 음식점(FD6)만 대상, **카페(CE7) 제외**, 카테고리명이 **야간 전용 업종**(술집/호프/바/포차/포장마차/야식 등)이면 제외.
    - (선택·정확) 실제 점심 영업 여부를 수동 확인한 **제외/포함 오버라이드** 목록으로 보정.
  - 최종 영업여부는 표시하지 않고(창작 금지) **카카오맵 링크로 위임**한다.
- 위 조건을 통과한 후보 중 **최근 N개(기본 예: 10) 추천 이력을 제외**하고 무작위 1곳 선택.
- 후보가 이력으로 모두 소진되면 가장 오래된 것부터 다시 후보에 포함(순환).
- **추천 분포는 특정 식당에 치우치지 않는다.** 이력 제외를 배제한 상태에서 충분히 반복하면 각 후보가 고르게 선택되어야 한다. 반복 방문을 직접 막는 것은 이력 제외지만, 그 선택 메커니즘 자체가 특정 식당을 구조적으로 편애·배제하면 "늘 가던 곳만"(§1) 문제가 다른 형태로 남는다.
- **대표 메뉴 힌트 제시**: 추천 식당의 `category_name`(업종)에서 대표 메뉴 힌트를 도출해 함께 보여준다.
  - 카테고리 **리프**가 이미 메뉴성이면 그대로 사용(예: `한식 > 국밥` → "국밥", `일식 > 돈까스,우동` → "돈까스/우동").
  - 리프가 막연한 상위 업종이면 **매핑표**로 대표 메뉴 제안(예: `양식` → 파스타/스테이크, `중식` → 짜장면/짬뽕, `분식` → 떡볶이/김밥).
  - 어디까지나 **"카테고리 기반 힌트"** 임을 명확히 표기하고, 실제 메뉴·가격은 카카오맵으로 위임한다(없는 메뉴 창작 금지).
- 결과에 **식당명, 업종/카테고리, 대표 메뉴 힌트, 거리(직선 기준 · 도보 약 N분 근사임을 표기), 지도상 위치, 카카오맵 링크**를 표시.
- **후보 0 처리**: 필터(반경·점심영업·이력) 후 후보가 없으면 오류 없이 안내하고 **반경 확대 / 이력 초기화**를 제안한다.
- 추천 이력은 브라우저에 유지되어 재방문 시에도 안 겹친다.
- **탭 구조**: 최상단에 3개 탭을 둔다 — **탭1(기본)** 오늘 점심 추천(UC1~UC5, 무변경) · **탭2 모락모락**(UC6) · **탭3 점심메뉴 월드컵**(UC7). 탭 전환은 화면 내 토글이며 별도 라우팅·페이지 이동은 없다.
- **모락모락(탭2) 기능 요구**: 회사 구내식당(풀무원 모락모락)의 오늘의 메뉴를 **GitHub Actions 예약 워크플로가 서버사이드로 수집해 커밋한 `data/moremore-latest.json`을 브라우저가 같은 오리진에서 fetch**해 코너별 카드(이미지·kcal·한글/영문 메뉴명·사이드메뉴)로 보여준다(브라우저에서 이 API를 직접 fetch하면 CORS로 차단됨을 실측 확인했다 — §8). 조회·표시 실패는 사유를 구분해 보여주지 않고 **모두 동일한 하나의 "준비중입니다" 안내**로 귀결한다(사용자에게는 실패 원인이 무엇이든 같은 화면) — **4경로 통합**:
  1. fetch 실패(네트워크 오류·비2xx 응답)
  2. 응답은 200이지만 데이터가 빈 배열
  3. 파싱 중 예외(필드 형식이 기대와 다름 등)
  4. **날짜 불일치** — 데이터의 `fetchedDate`가 오늘(KST) 날짜와 다름(Actions 갱신 실패·주말 등으로 구 데이터가 남아있는 경우, 어제/그제 메뉴를 오늘 메뉴로 오인시키지 않기 위한 창작 금지 조치)

  - **사진 표시**: 코너 카드의 사진은 벤더가 제공한 **원본 해상도 비율 그대로** 보여주며 임의로 크롭하지 않는다(실측 해상도 비율이 코너마다 1.36~1.71로 제각각이라 고정 비율 크롭은 원본을 왜곡한다). 사진이 없거나(코너 미제공·업로드 전) 로드에 실패하면 외부 이미지·가짜 사진으로 대체하지 않고 **"사진 없음"** 플레이스홀더로 폴백한다(창작 금지) — 문구를 "이미지 준비 전"이 아니라 "사진 없음"으로 정한 이유는, 라면(TAKEOUT)·석식처럼 **끝내 이미지가 제공되지 않는 코너**가 있어 "준비 전"은 오지 않을 사진을 약속하는 정직 표기 위반이기 때문이다.
  - **데이터 특성(사실)**: 벤더(풀무원 모락모락)는 **코너에 따라 사진을 끝내 제공하지 않을 수 있고**, 제공하는 코너도 **당일 중 늦게(오전 수집 시점엔 없다가 이후) 업로드**한다 — 실측: 2026-08-27 KST 10:11 수집 시 백반·스페셜의 이미지 필드가 `null`이었다가 11:12 재조회 시 업로드돼 있었고, 메뉴명도 함께 갱신됐다(`쫄면순두부찌개`→`뚝배기쫄면순두부찌개` 등). 반면 라면(TAKEOUT)·석식은 11:12 시점에도 `null`이었다 — 코너에 따라 끝내 이미지가 없을 수 있다. 이 특성이 §7의 오후 슬롯(15:17/17:33) 추가 근거이기도 하다.

  상시 서버·프록시를 두지 않는다(constitution 1, §7) — Actions 워크플로는 예약 빌드 작업일 뿐 상시 서버가 아니다.
- **점심메뉴 월드컵(탭3) 기능 요구**: 탭1이 반경 내에서 수집한 실제 후보 식당에 메뉴 힌트를 붙인 쌍(식당, 메뉴텍스트) 중 유효한 힌트가 있는 것만 참가 후보로 삼는다. 16개를 무작위로 뽑아 16강(8경기)→8강(4경기)→4강(2경기)→결승(1경기), 총 15경기의 토너먼트를 진행한다. 매 라운드 참가자는 정확히 절반으로 줄고 패자는 재등장하지 않는다. 매치 화면은 카테고리 이모지(실사진 아님을 명시)·메뉴명·식당명을 좌우로 보여주고, 우승 시 실제 식당명과 카카오맵 링크(`place_url`)로 연결한다. 참가 가능한 후보(유효 힌트 보유)가 16개 미만이면 대회를 지어내지 않고 안내 + 반경 확대를 제안한다.

## 5. 비기능 요구
- 버튼 클릭 → 결과까지 **3초 이내**. 이 약속은 **측정 가능해야 한다** — 소요시간을 기록해 확인할 수 있어야 하며, 측정 수단이 없으면 지켜지는지 알 수 없다. 판정 방식은 [plan.md](plan.md) 계측 절을 따른다.
- 모바일 우선 반응형, 다크/라이트 대응.
- 완전 정적·무료 배포. 서버·계정·개인정보 수집 없음.

## 6. 성공 기준 (Done)
- 한 번의 클릭으로 반경 내 **최근과 겹치지 않는** 식당 1곳을 지도·거리·카카오맵 링크와 함께 제시한다.
- 같은 사용자가 연속으로 눌러도 최근 N회는 서로 다른 곳이 나온다.
- 추천 식당은 **도보 15분(직선 ≈1km) 이내**이고, **야간 전용 업종(술집/바 등)은 제외**된다.
- 추천 식당의 **대표 메뉴 힌트**가 업종 기반으로 함께 표시된다.
- 필터 후 후보가 없어도 오류 없이 **안내와 대안(반경 확대/이력 초기화)** 을 보여준다.
- 반복 추천 시 **특정 식당에 쏠리지 않는다** — 고정 후보집합·이력 제외 비활성 상태에서 충분히 시행했을 때 후보별 선택 빈도가 균등에서 유의하게 벗어나지 않는다(판정 파라미터는 [oracle.md](oracle.md) D10).
- 추천 로직 설명 팝업의 조건 값(반경·최근 제외 개수 등)은 항상 실제 config 값과 일치한다(하드코딩된 별도 문구 없음).
- 모락모락(탭2)은 데이터 조회 실패(네트워크/CORS·빈 응답·파싱 오류·날짜 불일치 중 무엇이든)를 하나의 동일한 "준비중입니다" 안내로 보여준다.
- 모락모락(탭2) 카드의 사진은 원본 해상도 비율 그대로 표시되고(고정 비율 크롭 없음), 사진이 없거나 로드 실패 시 실제 사진 대신 "사진 없음" 플레이스홀더로 대체된다(가짜 사진 없음).
- 점심메뉴 월드컵(탭3)은 탭1이 수집한 실제 후보(메뉴 힌트 보유)만으로 16강~결승 15경기를 진행하며, 각 라운드는 참가자 수가 정확히 절반이 되고 패자는 재등장하지 않는다.
- 참가 가능 후보가 16개 미만이면 지어내지 않고 안내(반경 확대 제안)로 대체한다.
- 월드컵 우승 시 실제 식당명과 카카오맵 링크(`place_url`)가 함께 표시된다(가짜 링크 없음).

## 7. 범위 밖 (Non-goals, 현재)
- 팀 투표·공유 이력(백엔드 필요) — 개인용 원칙상 제외.
- 로그인/계정, 서버 저장.
- **실시간 영업여부·정확한 영업시간·상세 메뉴/가격 크롤링** — Kakao 검색 API 미제공. 카카오맵 링크로 위임(§4 점심 영업 제약, §8 참조).
- **모락모락 상시 서버 프록시**(요청마다 실시간으로 대신 호출해주는 백엔드)는 범위 밖이다(백엔드 없음 원칙, constitution 1). GitHub Actions 예약 워크플로가 정적 파일(`data/moremore-latest.json`)을 평일 **KST 07:13~17:33 사이 9슬롯**(07:13/08:29/09:41/10:07/11:23/12:37/13:51/15:17/17:33)으로 재시도 갱신하는 것은 상시 서버가 아니라 예약 빌드 작업이라 이 원칙과 배치되지 않는다(§4). GitHub Actions 예약(cron)은 best-effort라 슬롯 하나가 드롭·지연돼도 뒤 슬롯이 재시도하도록 다중화했을 뿐이며, 그 다중 슬롯이 모두 실패하거나 그날 갱신 자체가 끝내 안 되면 우회(백엔드 프록시·클라이언트 직접 호출 대체) 없이 종전과 동일하게 "준비중입니다"로 안내한다.

- [ ] **점심 영업 판별의 정확도** — Kakao가 영업시간을 안 주므로 §4의 근사(카테고리 제외 + 수동 오버라이드)로 처리. 정확도가 부족하면 추후 (a) 소수 대상 수동 큐레이션 확대 또는 (b) 영업시간 제공 데이터소스 검토. **자동만으로 100% 보장은 불가**함을 사용자에게 고지.
- [x] **"메뉴 추천" 범위 확정**: 개별 메뉴/가격은 미제공 → `category_name` 리프 + 매핑표로 **대표 메뉴 힌트**를 도출해 제시(창작 금지, 상세는 카카오맵 위임). 도출 규칙은 [plan.md](plan.md) "메뉴 힌트 도출". 상세 메뉴 DB 큐레이션은 향후 선택.
- [ ] 반경 후보가 너무 많을 때 카테고리 필터(한식/양식/매운거 등) 도입 여부(후속).
- [x] **모락모락 CORS 실증** — **확인됨(2026-08-25)**: 브라우저 직접 fetch는 CORS로 차단됨(응답에 `Access-Control-Allow-Origin` 헤더 없음, 실측 확인). 반면 GitHub Actions 러너에서 서버사이드로 호출하면 정상 동작함(HTTP 200, 실 데이터 수신, 실측 검증 — `.github/workflows/verify-moremore-fetch.yml`). 이에 따라 아키텍처를 "브라우저 직접 fetch"에서 "Actions 예약 크롤러가 수집·커밋한 정적 파일을 같은 오리진에서 fetch"로 전환했다(§4).
- [ ] **Actions 예약 실행 실패·지연 시 방치 기간** — 실측(2026-08-26 예약분 1시간 지연 발동, **2026-08-27 예약분은 발동 자체가 없었음**)에 따라 평일 KST 9슬롯(07:13~17:33) 재시도로 완화했다(§4, [plan.md](plan.md) 모락모락 크롤러 워크플로 스케줄). 저장 게이트는 `hasMoremoreItems(raw)`로 "빈/이상 응답이면 저장하지 않는다" 한 가지만 판정한다. 이 판정에 실패(빈/스키마 깨진 응답)했을 때 워크플로 자체를 실패(`exitCode=1`)시킬지는 **환경변수 `MOREMORE_STRICT`로 슬롯마다 다르다** — 워크플로가 **KST 17:33 슬롯(당일 마지막 슬롯)일 때만 `1`**을 주입하고, 그 외 슬롯·`workflow_dispatch`는 `0`이다. `MOREMORE_STRICT=1`이고 **저장된 파일의 `fetchedDate`가 오늘이 아닐 때만** 실패시킨다(앞선 슬롯이 이미 오늘 데이터를 확보했다면 마지막 슬롯의 빈 응답은 실패로 보지 않는다). 벤더가 당일 중 데이터를 점진적으로 채우므로 이른 슬롯의 빈 응답을 매번 실패로 띄우면 평일마다 빨간 잡이 쌓여 "빨간 워크플로 = 이상 신호"라는 전제 자체가 죽기(경보 피로) 때문이다. **능동 알림 수단이 없는 상태에서 이것이 유일한 이상 탐지 신호**이며, 이제는 **"하루가 끝났는데 오늘 데이터를 끝내 확보하지 못했다"**는 진짜 이상일 때만 붉게 뜬다. 이 신호는 정직하지만 여전히 부작용이 있다: **실제로 메뉴가 없는 공휴일에는 하루 최대 1건(당일 마지막 슬롯)** 워크플로가 붉게 뜬다(이전엔 슬롯마다 최대 9건이었다). `isFreshMoremoreData`로 날짜 불일치 시 "준비중"으로 오인 표시는 여전히 막는다. 다만 다중 슬롯도 GitHub 예약(cron)의 best-effort 한계 안에 있어 그날 슬롯이 전부 드롭되면 여전히 미갱신 상태로 남을 수 있다.
- [ ] **KST 자정 경계에서의 창작 금지 위반 가능성** — `workflow_dispatch`를 KST 00:0x 시각에 수동 실행하면 `getKstYyyymmdd()`(`scripts/fetch-moremore.mjs`)는 새 날짜를 반환하지만, 벤더 API는 아직 어제 메뉴로 응답할 수 있다. 이 스크립트는 응답 안의 날짜와 요청 날짜를 대조하지 않으므로, **어제 메뉴에 오늘 날짜 라벨(`fetchedDate`)이 붙어 그대로 커밋될 수 있다** — constitution 3(창작 금지)이 막으려는 것과 같은 종류의 오인 표시 경로다. 저장 게이트(`hasMoremoreItems`)는 "응답에 항목이 1개 이상이면 항상 저장"만 판정하고 날짜 자체는 보지 않으므로, 이 경로에는 저장 단계의 방어막이 없다(방어는 오직 클라이언트 쪽 `isFreshMoremoreData`가 "오늘 라벨이 붙었지만 실제로는 어제 메뉴"인 내용까지는 구분하지 못한 채 라벨만 믿고 렌더한다는 뜻). 예약 슬롯(07:13~17:33)에서는 자정과 거리가 있어 발생하지 않으며, 수동 실행을 자정 근처에서 하지 않는 것으로만 회피되는 상태다(코드 수정 없이 남은 미해결 항목).
- [ ] **알림 수단 부재** — 워크플로 실패(빨간 표시) 외에 사용자·운영자에게 능동으로 알리는 수단(Slack 등)이 없다. 갱신 실패가 며칠 지속돼도 GitHub Actions 탭을 직접 확인하지 않으면 알 수 없다(후속 검토로 남음).
- [ ] **`git pull --rebase` 실패 시 슬롯 유실** — 커밋 스텝에서 `git pull --rebase`가 리베이스 충돌로 실패하면 그 슬롯의 수집분은 커밋되지 못하고 유실된다. 재시도 루프가 없어 그 슬롯 자체는 실패로 끝나며, 대신 뒤따르는 다음 슬롯이 다시 수집을 시도해 메운다(9슬롯 다중화가 이 유실의 실질적 완충 역할).
