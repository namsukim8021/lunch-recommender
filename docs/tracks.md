# Verification Tracks — 검증 트랙 5종 (HOW TO JUDGE)

> [oracle.md](oracle.md)가 "**무엇이 정답인가**"(정답의 출처)를 정한다면, 이 문서는 "**그 정답으로 언제 무엇과 비교해 판정하는가**"를 정한다.
> 개념 배경: 스터디 4회차 — 검증 트랙 5종(Regression / Migration / Extension / Signal / Probabilistic).

## 0. 왜 별도 문서인가

오라클을 정의한 것만으로 검증이 끝나지 않는다. 같은 "정답"이라도 **무엇과 비교할지(레퍼런스)** 와 **언제 판정할지(시점)** 가 변경 유형마다 다르기 때문이다.

그리고 이 문서의 핵심 발견은 이것이다 — **트랙은 다 만든 뒤 고르는 검증 메뉴가 아니라, 코드를 쓰기 전으로 거슬러 올라오는 설계 제약이다.** 각 트랙에는 선행 조건이 있고, 그걸 Phase 5 구현에 미리 심지 않으면 나중에 그 트랙을 아예 열 수 없다.

## 1. 트랙 5종과 선행 조건

| 트랙 | 무엇과 비교 | 시점 | 이 트랙을 열려면 미리 필요한 것 |
|---|---|---|---|
| Regression | A vs A′ (과거의 나) | 배포 전 | 재현 가능한 golden = **결정성** |
| Migration | A vs B (다른 구현체) | 배포 전 | 비교 가능한 **두 번째 구현체** |
| Extension | A + α vs Spec | 배포 전 | 판정 가능한 **스펙(AC)** |
| Signal | σ(A) vs σ(A′) — 지연·리소스·호출 패턴 | **배포 후** | **관측점(계측)** + 베이스라인 |
| Probabilistic | P(A) ≈ P(A′) — 출력의 분포 | 배포 전·후 | **반복 실행** = 결정성 + 시뮬레이션 |

> **레퍼런스는 콜드 스타트에서 한 번 바뀐다.** Regression의 golden이 없듯 Probabilistic도 처음엔 비교할 `P(A′)`가 없다. 그래서 첫 판정의 레퍼런스는 **스펙이 정한 이론 분포(균등, D10)** 이고, 첫 구현이 수용되면 그때의 분포가 박제되어 이후 **`P(A′)` 대비 비교**로 전환된다 — [oracle.md §2](oracle.md)의 콜드 스타트 논리와 같은 구조다.

맨 오른쪽 열이 이 문서의 실질이다.

## 2. 오라클 3층 ↔ 트랙 5종

| [oracle.md](oracle.md) — 정답의 출처 | 이 문서 — 판정 방법 |
|---|---|
| ③ 바이너리 오라클 | Regression · Migration |
| ① 명세 오라클 | Extension |
| ② 도메인 오라클 | **대응 트랙 없음** — 어느 트랙에서도 항상 켜져 있어야 할 상시 안전망 |
| (신설) 분포 요구 — `spec §4`·D10 | Probabilistic |

도메인 오라클(D1~D10)에 전용 트랙이 없는 것은 결함이 아니다. 특정 변경을 판정하는 장치가 아니라 **모든 트랙에서 상시 켜져 있어야 하는 안전망**이기 때문이다.

## 3. 이 프로젝트의 현재 상태

Phase 5(구현) 미착수 = **바이너리 오라클 콜드 스타트**. 이 상태에서 다섯을 붙이면 아래처럼 갈린다.

| 트랙 | 지금 가동? | 막고 있는 것 / 열기 위해 필요한 것 |
|---|---|---|
| **Extension** | 📝 **기준만 확립** | 다섯 중 유일하게 **레퍼런스가 이미 존재**한다(`spec §6` AC + 도메인 D1~D10). 다만 `A + α`(코드)가 없어 실제 판정은 Phase 5 — 즉 "열려 있다"가 아니라 "열 준비가 된 유일한 트랙"이다 |
| **Regression** | ❌ 불가 | 비교할 A가 없다(콜드 스타트). 구현이 생겨도 **결정성**이 없으면 golden을 못 만든다 → [plan.md 추천 로직 결정성 불변식](plan.md) |
| **Probabilistic** | ❌ 불가 | 추천이 랜덤이라 **본질적으로 이 트랙의 대상**인데, 분포를 뽑으려면 역시 결정성 + 반복 실행이 필요. 레퍼런스는 콜드 스타트라 이론 분포(D10) |
| **Migration** | ➖ 해당 없음 | 구현체가 하나뿐. **Kakao SDK를 다른 지도 SDK로 교체**하는 순간 발동 |
| **Signal** | ❌ 불가 | 정적 사이트라 서버 메트릭이 없다. σ를 볼 곳이 없는 게 아니라 **σ를 만들 코드를 안 넣었을 뿐** → [plan.md 계측](plan.md) |

### 3-1. Regression과 Probabilistic은 설계 결정 하나에 함께 걸려 있다

교재상 가장 멀리 떨어진 두 트랙("값이 똑같아야 한다" vs "값은 달라도 분포가 같아야 한다")이 이 프로젝트에서는 **같은 벽**에 막힌다.

```
추천 = 반경 내 후보 중 "랜덤" 1곳

Regression     golden 스냅샷을 만들려면  → 매번 같은 결과   → 시드 고정 필요
Probabilistic  분포를 비교하려면          → 수천 번 반복 실행 → 시드 고정 필요

표준 Math.random() 은 시드를 넣을 수 없다
  → 난수원을 "주입 가능"하게 설계해야 한다
  → 이건 검증 코드가 아니라 프로덕션 코드의 구조 결정이다
```

`plan.md`의 **결정성 불변식**(난수원 파라미터화)이 그래서 검증 편의가 아니라 **아키텍처 제약**이다. Phase 5에서 이 결정을 빠뜨리면 두 트랙이 동시에 닫힌다.

### 3-2. Signal은 "관측점이 없다"는 형태로 막힌다

`spec §5`에 이미 후보가 하나 있다.

> "버튼 클릭 → 결과까지 **3초 이내**"

이 문장은 현재 **아무도 측정하지 않는 약속**이다. Signal Track을 열려면 클릭→결과 구간을 계측해 남기는 코드가 필요하고, 이것 역시 Phase 5에 미리 넣어야 한다.

정적 사이트라 서버 APM은 없지만, 이 프로젝트에서 σ에 해당하는 것은 있다.

| σ 후보 | 무엇을 보나 | 왜 응답 비교로는 안 잡히나 |
|---|---|---|
| 추천 소요시간 분포 | 클릭 → 결과 카드까지 | 추천 결과가 같아도 격자 타일 수가 늘면 느려진다 |
| Kakao 검색 호출 수 | 한 번의 추천에 몇 번 검색했나 | 결과가 같아도 호출이 3배면 쿼터·요금이 다르다 |
| 후보 수집 개수 | 필터 전/후 후보 수 | 격자 피복이 깨져 후보가 조용히 줄어도 추천은 정상으로 보인다 |

**⚠️ 지금 하는 것은 엄밀히는 Signal이 아니다.** 계측값을 `spec §5`의 절대 임계(3초)와 대조하는 것은 레퍼런스가 스펙이므로 **명세 오라클**이다. 진짜 Signal(σ(A) vs σ(A′))은 배포 전후 베이스라인이 있어야 성립하는데, 아직 배포된 A가 없다.

즉 이 단계에서 하는 일은 **Signal Track의 관측점을 미리 확보하는 것**이고, 계측이 쌓여 베이스라인이 생기면 그때 σ 비교로 승격한다. 이 구분을 흐리면 "계측만 넣으면 Signal 하는 것"이라는 착각이 생긴다.

**실무 교훈(승격 시 적용)**: 표본이 작으면 p99는 사실상 최댓값이라 분포 비교가 아니라 단일 이벤트 감지가 된다. 개인용이라 시행 횟수가 적으므로 판정은 **비율(몇 배)이 아니라 절대값(몇 ms·몇 회)** 기준으로 잡는다.

### 3-3. 3탭 확장(모락모락·월드컵) — Extension 트랙 신규 가동

이번 3탭 확장(탭2 모락모락·탭3 월드컵)은 **Extension 트랙**(`A + α vs Spec`)으로 판정한다. 두 기능 모두 신규라 비교할 기존 동작(A)이 없고, 레퍼런스는 `spec §6`의 신규 AC(모락모락 3경로 통합·월드컵 라운드/후보 요구)와 도메인 오라클 D12~D15다 — [oracle.md §2 콜드 스타트](oracle.md) 논리와 같은 구조: 판정 기준은 확립됐으나 통과시킬 코드는 다음 구현 단계에서 만들어진다.

탭1(기존 오늘 점심 추천)이 이미 열어 둔 Regression·Probabilistic·Signal 트랙의 전제(난수원 주입 `pickRandom(list, rng)`, `elapsedMs`/`searchCalls`/`candidateCount` 계측)는 이번 확장으로 **깨지지 않는다** — `app.js`에는 getter 노출 한 줄만 추가되고 기존 로직은 무수정이며, 월드컵의 16개 추출도 주입 가능 `rng`를 쓰므로(plan.md 테스트 관점의 "월드컵 결정성" 항목) 탭1의 결정성 설계와 같은 원칙을 따른다. 즉 이번 확장은 기존 세 트랙을 닫지 않고, 새 Extension 판정 하나를 여는 변경이다.

## 4. 변경 시 — 어떤 트랙으로 판정하나

[oracle.md §4](oracle.md)의 오라클 선택 표에 대응하는 트랙 열이다.

| 변경 유형 | 트랙 | 레퍼런스 |
|---|---|---|
| 리팩터(동작 불변) | Regression | golden |
| 동작이 바뀌는 수정 | Extension → (수용) → Regression | spec AC → 새 golden |
| 신규 기능 | Extension | `spec §6` AC |
| 지도 SDK·데이터소스 교체 | Migration | 기존 구현의 출력 |
| 성능·호출량에 영향 있는 변경(격자 타일 크기 등) | **Signal** | 베이스라인 확보 전: `spec §5` 절대 임계 → 확보 후: 이전 계측 |
| 추천 알고리즘·이력 정책 변경 | **Probabilistic** | 콜드 스타트: 이론 분포(균등, D10) → 수용 후: 이전 분포 |

PR·리뷰 때 한 줄 질문이 하나 늘어난다.

> oracle.md: **"이 변경의 정답은 뭘로 정해져 있나?"** (golden? AC? 도메인 규칙?)
> tracks.md: **"그 정답과 언제 무엇을 비교할 건가?"** (어느 트랙인가)

## 5. 성숙도 — 트랙 기준 자가 진단

| 트랙 | 상태 |
|---|---|
| Extension | 📝 판정 기준 확립(문서) · ⏳ 자동 실행은 Phase 5 |
| Regression | 🔲 콜드 스타트 — 수용 시 golden 박제 |
| Probabilistic | ✅ 판정기 구현 — 분포 요구(`spec §4`·D10)는 정의됨, `scripts/oracle-check.mjs`에서 D10 카이제곱 검정 실행 |
| Signal | ⏳ 관측점 확보 — `app.js`에 `elapsedMs`/`searchCalls`/`candidateCount` 계측 배선 완료(`localStorage["lunch_metrics"]`). 단 **베이스라인·실측 판정은 미실시**(배포 후 실사용 데이터 필요) — 진짜 Signal(σ(A) vs σ(A′))로 승격 전 |
| Migration | ➖ 해당 없음 |
